# التطوير والمساهمة

## قواعد عملية قبل أي تعديل

1. افهم ترتيب الأنظمة قبل التعديل (خصوصًا التخطيط/الرندر/التفاعل).
2. لا تكسر `Reflection` للأنواع العامة بلا سبب.
3. اختبر التعديل على أمثلة فعلية وليس فقط اختبارات الوحدة.
4. عند إضافة وحدة جاهزة جديدة:
   - واجهة مكوّن واضحة
   - إضافة مستقلة
   - رسائل الأحداث إن لزم
   - مثال توضيحي
   - توثيق في ملف التعريف وهذا الكتاب

## مكان التوثيق والأمثلة

- أضف أي صفحة شرح جديدة في `docs/src/en` و`docs/src/ar` معًا.
- ضع المثال الجديد داخل الـ crate التي تملك الميزة.
- اترك الجذر `examples/` فقط لعروض الواجهة المجمعة المتكاملة.
- اتبع القواعد المذكورة في [قواعد تحرير التوثيق](editorial-rules.md).
- اتبع [اصطلاحات التسمية](naming-conventions.md) عند تقسيم الوحدات الداخلية أو إعادة تسميتها.
- راجع [خريطة الصيانة](maintainer-map.md) و[قواعد المعمارية](architecture-rules.md) قبل نقل حدود الملكية أو التبعيات.
- راجع [اتفاقيات بنية الوحدات الجاهزة](widget-structure.md) و[حدود محرك التخطيط](layout-engine-boundaries.md) قبل تقسيم subsystem كبيرة.
- راجع [مسار تأليف التوثيق](authoring.md) للخطوات الدقيقة المتعلقة باللغتين و`rustdoc`.
- استخدم [قائمة مراجعة التوثيق](review-checklist.md) قبل الدمج.

## أسلوب الكود داخل المشروع

- يعتمد على ECS أولًا.
- مكونات صغيرة وأنظمة واضحة.
- سلوك مرئي عبر `UNode/UBorder/UInteractionColors`.
- تجنب آثار جانبية غير متوقعة خارج الجدولة المقصود.

## فروع العمل المقترحة

- `feat/<name>` للميزات.
- `fix/<name>` للإصلاحات.
- `docs/<name>` للتوثيق.
